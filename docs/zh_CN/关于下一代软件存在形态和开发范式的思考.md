# 关于下一代软件存在形态和开发范式的思考

## 摘要

随着大语言模型（LLM）能力的飞速提升，我们对"软件是什么"这一根本问题的理解正在发生深刻变化。传统的软件开发范式建立在四个隐含前提之上——确定性、静态性、人类中心、过程中心——这些前提在过去数十年中从未被真正质疑过。然而，当我们试图将大模型的能力融入软件系统时，却发现当下的AI应用仍然停留在将大模型作为"超级工具"、与传统程序强行拼合的阶段。大模型被降格为一个可调用的API端点，其理解、推理与生成能力被限制在预定义的管道之中，无法从根本上改变软件的存在形态。

针对这一困境，我们提出了一种新的软件存在形态和开发范式——**Vigorware（活软件）**。它不是对现有软件架构的增量改良，而是在根基层面重新定义软件与智能的关系。Vigorware具备以下六项核心特征：

1. **LLM第一性**：LLM不再是软件的外挂组件或辅助工具，而是整个软件系统的第一性推理引擎。软件的核心控制流、决策逻辑与生成过程均以LLM的推理能力作为基石，系统架构围绕LLM的能力边界与交互模式进行原生设计。
2. **意图驱动开发**：开发者不再需要将模糊的业务意图逐行翻译为确定性的指令序列。取而代之的是，开发者以自然语言或高层语义约束来表达"做什么"，由系统自身完成从意图到实现的推理与映射。开发的核心工作从编写代码转向表达意图、定义约束与建立验证标准。
3. **模糊性共存**：传统软件将所有的模糊性视为缺陷，要求在编译期消除一切不确定性。Vigorware则承认并拥抱模糊性作为系统的一等公民。概率性推理、置信度传播、近似匹配等机制被纳入语言和运行时的核心设计中，使得软件能够像人类一样在不完全信息下做出合理决策。
4. **原生感知**：软件不再是一个封闭的指令执行器，而是具备对运行环境、用户行为、数据分布乃至自身状态进行持续感知的能力。这种感知并非简单的日志采集或指标监控，而是系统内建的、与业务逻辑深度耦合的认知能力——软件能够理解"正在发生什么"以及"这意味着什么"。
5. **自我进化**：Vigorware具备在运行期间根据感知到的反馈信号，对自身的行为逻辑、代码结构乃至架构模式进行自主调整与优化的能力。这不是传统意义上的热更新或配置变更，而是软件作为一个有机体，根据实际运行数据与业务效果，持续改写自身的实现——从参数调优到策略重构，直至进化出开发者未曾预见的解决方案。
6. **完全可解释性**：在引入模糊性与自我进化机制的同时，Vigorware要求系统的每一个决策路径、每一次推理过程、每一项自我修改都必须是可追溯、可审计、可理解的。这既是工程可靠性的底线要求，也是人类对自主系统保持信任与控制的前提条件。不可解释的"黑箱自治"不在Vigorware的设计目标之内。

## 1. 前言

自图灵机模型和冯·诺依曼架构奠基以来，计算机科学在数十年的发展中积累了一整套关于"程序是什么"的隐含假设。这些假设如此根深蒂固，以至于它们从未作为"假设"被明确陈述，更遑论被系统性地质疑。我们可以将其归纳为四项基本前提：

1. **确定性**：对于相同的输入，程序总是产生相同的输出。计算的本质是一个从输入到输出的确定性映射。
2. **静态性**：程序的行为在编译（或部署）时即已确定，运行时不会自发地改变自身的逻辑。代码是静止的文本，只有人类才能修改它。
3. **人类中心**：人类是程序设计中唯一的思考发动者。所有的抽象、建模、架构决策，都是人类智力活动的产物。计算机是一台忠实的执行机器，它不理解"为什么"，只执行"怎么做"。
4. **过程中心**：软件开发的核心任务，是将人类脑中模糊的业务意图，逐步翻译、分解、编码为精确的指令序列。意图的表达与意图的实现之间，横亘着一道由人类程序员手工架设的翻译之桥。

这四项前提共同构成了传统软件范式的基础公理。在这一范式下，现实世界的复杂性、模糊性和不确定性，只能通过人类程序员的智力劳动来消解——将混沌的真实世界抽象为整洁的确定性模型、将模糊的业务需求精炼为精确的算法流程、将动态的运行环境封装为静态的配置参数。软件工程的全部方法论，从结构化编程到面向对象设计，从设计模式到微服务架构，本质上都是在这四项公理框架内寻找更优雅的解法。

早期的机器学习技术——从感知机到支持向量机，从决策树到浅层神经网络——曾让人们看到一丝希望：也许机器可以自主地从数据中学习规律，完成人类难以手动编码的复杂感知与决策任务。然而，这些技术在当时并未触及上述四项前提的根基。它们仍然作为确定性管道中的一个功能模块而存在——一个经过训练后行为固定的分类器或回归器，嵌入在人类预先设计的、静态的程序流程之中。软件的本质未曾改变。

真正的转折点，出现在基于深度学习技术的各类模型，特别是基于Transformer架构的大语言模型身上。LLM所展现出的并不仅仅是更高的分类准确率或更好的序列预测能力，而是一种质的飞跃：**对自然语言的深层理解、对复杂意图的推理规划、对开放性问题的生成式回应**。这意味着机器第一次拥有了从"执行者"跃迁为"思考发动者"的潜力——它不仅能按指令行事，还能理解目标，分解任务，甚至提出人类未曾考虑过的解决路径。

然而，当我们审视今天将LLM能力与软件系统结合的主流实践时，会发现一幅令人遗憾的图景：几乎所有的尝试，仍然和过去使用感知机、支持向量机、决策树、浅层神经网络一样，都是在旧范式的框架内为LLM寻找一个安放的位置。LLM被封装为一个API调用，插入到传统的请求-响应管道中；被包裹在精心设计的Prompt模板里，扮演一个高级的文本处理函数；被部署在Agent框架的循环中，模拟一个按预定义工具列表行事的自动化脚本。这些做法的共同特征是：**软件的基本架构未曾改变，只是在其中多了一个名为"LLM"的组件**。

这并非一个仅靠迭代工程实践就能逐步克服的技术问题。当我们试图用确定性的管道约束本质上具有概率性的推理引擎，用静态的程序结构承载本应自我演化的智能行为，用人类中心的开发流程去驯服一个具备独立思考潜力的模型时，我们面对的不是某个环节的效率瓶颈，而是**范式层面的根本性错配**。

针对这一现状，我们认为：一种新的软件存在形态和开发范式，正在悄然成形。但大部分实践者的思想仍囿于旧范式的思维定式之中，即便在某些项目中偶然触及了新模式的个别特征，也缺乏对新范式全貌的系统性认知。这正是当下AI应用虽层出不穷，但真正具有范式突破意义的软件仍然稀缺的根本原因。我们将这一正在浮现的新范式命名为**Vigorware（活软件）**——它不是对旧范式的修补，而是在新的基础公理之上重建软件的定义。

## 2. 当下AI软件的尝试与局限

在我们正式叙述Vigorware之前，有必要先梳理当前将大语言模型融入软件系统的实践路径及发展历程，并分析它们各自的局限性。

### 2.1 聊天机器人与图像识别器

在AI Agent概念出现之前，LLM的存在形态主要是作为聊天机器人。用户通过文本与LLM进行交互，LLM根据用户的输入生成回复。与程序开发相关的尝试，仅限于在聊天框中让LLM生成代码片段，或者让LLM解释代码的含义，再由人类开发者复制到IDE中运行。即便在之后出现了AI自动代码生成工具，如GitHub Copilot、Tabnine，但其本质仍然与之前区别不大，只是将人工手动复制粘贴的操作自动化了而已。虽然在此过程中，即使LLM展现出了一定的思考发动主体的特征，大幅提升了开发效率，但本质上仍然是一个加强版的代码补全工具，其思考发动仍然局限于人类的思维边界。

而此时的视觉、音频等其他模态领域，其存在形态仍与传统软件无异，只作为一个“识别率更高”，或“生成效果更好”的工具存在于传统的软件流程中。

### 2.2 AI编排工具

随着模型能力的提升，人们开始尝试有限度地将LLM作为思考发动主体，设计工具链，将其整合到传统的软件流程中。例如，LangChain、LlamaIndex等框架的出现，使得开发者能够方便地将LLM与其他工具（如数据库、API、文件系统等）进行编排，构建出能够处理复杂任务的AI应用。另外，一些整合了LLM的低代码平台，如n8n、Dify、Flowise等，也允许用户通过可视化的方式编排LLM与其他工具，构建出能够处理复杂任务的AI应用。这类应用通常包含以下几个核心组件：

1. **LLM**：作为思考发动主体，负责理解用户意图、生成推理路径、调用工具等。
2. **工具链**：由一系列工具组成，用于获取信息、执行操作、与外部世界进行交互。
3. **记忆**：用于存储上下文信息，包括对话历史、用户偏好、任务进度等。
4. **评估**：用于评估任务完成情况，包括任务是否完成、任务是否符合用户要求等。

这类AI编排工具虽然在一定程度上提升了AI应用的开发效率和功能性，但仍然存在一些局限性。例如，LLM的输出仍然具有不确定性，可能导致任务执行失败；工具链的设计仍然依赖于人类的经验和智慧，需要人类进行大量的调试和优化；记忆的存储和检索仍然存在一些问题，可能导致上下文信息丢失或不准确。而根据记忆和评估对LLM的输出进行修正、以及对流程进行优化，仍然需要人类的干预。

### 2.3 Coding Agent

这一阶段的尝试，已经让模型的思考发动主体性融入到软件工程的主体环节。模型逐渐开始承担理解模糊意图、生成具体逻辑的任务。

### 2.4 “AI原生”编程语言

在近年来，人们逐渐意识到，现有的编程语言是为人类的思考习惯设计的。由于人类的思维方式和AI的思维方式存在差异，导致AI在使用这些语言进行编程的时候，效率低下。因此，人们开始尝试设计“AI原生”的编程语言，以尝试从不同领域贴合AI的思维模式，提升AI的编程效率，减少AI因幻觉等问题导致的程序设计问题。以下是一些代表性的尝试：

Jaseci（Jac）追求全栈统一抽象，用同一种语言描述前端、后端与数据模型，并通过“意义类型编程”将AI调用内嵌为语言特性。它的贡献在于证明了抽象与业务同构对LLM友好的价值，但未能触及软件运行时的自我优化。

Sever将AI深度集成进编译工具链，通过MCP协议让AI直接参与类型检查、AST分析与代码优化。它的贡献在于揭示了AI不应仅是代码生成者，更应是代码结构的“阅读者”与“操作者”，但它仍聚焦于编译时，未将这一思想延伸至运行时。

Codong以极简主义回应LLM的“选择困难”，将“每件事只有一种正确方法”作为语法铁律，并内置核心模块以消除依赖选择。它的贡献在于证明了语法空间的收敛是提升LLM生成准确率的最有效手段，但它将AI视为代码的消费者，而非软件生命周期的参与者。

Dana（认知企业平台）设计了COSTAR Agent生命周期与认知本体，让Agent从文档与交互中持续构建领域知识图谱。它的贡献在于将知识的外化与积累提升为核心抽象，但知识的应用仍依赖Agent推理，未能沉淀为可进化的代码本身。

这些探索各有侧重，分别在抽象统一、工具链集成、语法收敛、知识外化等维度上迈出了坚实步伐。然而，它们共同缺失了一个根本维度：软件自身的生命特征。它们依然将软件视为静态的文本——即便它由AI生成、即便它调用AI模型。软件在执行时是“凝固”的。
